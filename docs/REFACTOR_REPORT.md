# POPP’IN implementation report

Completed October 7, 2026. The approved Home design, existing records, palette and fonts are preserved. This report describes the new shared account/event platform; the earlier admin workflow is removed.

1. **Files changed.** Client: package files, `api/client.ts`, `router/AppRouter.tsx`, public header/footer/layout, `styles/app.css`, Discover/EventDetails/VendorApplication pages, existing organizer event/call/post forms, event formatting, announcement schema and domain types. Server: package files, `.env.example`, app mounting, JSON errors, all seven existing models, event/organizer/post/call/application/catalogue/upload routers, capacity helper, seed and poster importer. README/API/defense/requirements documentation is updated. `public.css`, Home JSX, fonts, illustration assets and the original poster dataset are retained.
2. **Files created.** Client auth provider/context/session/guards; `types/account.ts`; `useResource.ts`; external auth/profile/application-note schemas; shared FieldGroup/ImageUploader/EventCard/ProfileHeader/OrganizerIdentity/EventPostCard/VendorCard/StatusBadge/ResourceState/navigation; shared Feed/Opportunities pages and Auth/Profile/EditProfile/MyEvents/Applications/ConfirmedEvents screens. Server User/VendorProfile models; auth middleware; access/availability helpers; auth/profile/vendor/feed routers and migration script. New API/migration/report and browser verification artifacts are in `docs/`.
3. **Files removed.** AdminDashboardPage, old AdminManagementPage (working catalogue forms relocated), OrganizerDashboardPage, TrackApplicationPage, WorkspaceLayout, analytics type, unused useEvents loader, old tracking/application schemas, and backend admin analytics router. No active route imports the deleted code.
4. **New frontend npm dependencies.** None. React, React Router, React Hook Form, Zod, axios, Tailwind and the existing icons remain.
5. **Backend dependencies.** Added `bcryptjs` and `jsonwebtoken`. Removed frontend `recharts`, which was used by the deleted admin dashboard. Updated lockfiles.
6. **Models.** Added User and VendorProfile. Organizer gains an optional unique User link and logo; existing unclaimed IDs remain valid. Event uses draft/published/cancelled and a server publication timestamp. Announcement gains post types and optional image while keeping its collection. Applications link VendorProfile and use pending/accepted/rejected/withdrawn plus a unique vendor/call index. Catalogue records gain creator IDs; call/application writes use optimistic concurrency.
7. **Relationships.** User → organizer or vendor profile; organizer → events; event → venue/categories/posts/calls; vendor → applications → call → event. Post ownership comes from its parent event. There is no duplicate profile/post/confirmation collection. See the README diagram.
8. **Authentication.** Registration atomically creates User + required business profile. Passwords are hashed with bcrypt, excluded from default reads and omitted from responses. JWTs have an expiry, issuer, audience and fixed verification algorithm. One AuthContext persists/restores the session; one axios interceptor attaches tokens; guarded routes and backend role/owner checks enforce access.
9. **Client workflow.** Register/log in → shared feed → discover/filter → one event page → organizer updates/profile → accepted lineup/vendor profiles. Clients edit their own personal profile and can browse opportunities.
10. **Organizer workflow.** Register → complete linked profile → create draft → publish immediately → edit without returning to review → publish event updates → open recruitment → review own applications → accept/reject → accepted lineup updates automatically. Owner controls appear within the shared pages.
11. **Vendor workflow.** Register → complete reusable business profile → browse calls → apply with a note → view own decisions → withdraw a pending application → see confirmed/upcoming/past events. Server snapshots business details from the signed-in profile; forged request identity fields are ignored.
12. **APIs.** Added `/auth`, `/profiles/me`, `/vendors`, `/feed`, `/events/mine`, `/events/:id/vendors`, `/posts` and scoped management reads. Event status writes publish/cancel directly. Existing `/announcements` remains a secured alias. All current methods, permissions and examples are in [API.md](API.md).
13. **Admin dependencies removed.** No admin page, navigation link, workspace shell, verification endpoint, global admin analytics, pending event approval or approval-required publication remains. Legacy event review states are treated as drafts until manual normalization. Vendor application review remains an organizer responsibility.
14. **Ownership/security.** Accounts cannot assign roles, owners, application state, publication timestamps or reviewer identity through ordinary updates. Private lists are scoped to the signed-in vendor or event owner. Drafts are owner-only. Confirmed vendors can still read their own cancelled booking and published updates; other users cannot. Public application tracking is removed. Catalogue edits/deletes require the creator. Parent/reference and category rules are enforced server-side; acceptance capacity is transactional.
15. **Vendor Lineup.** Query accepted applications belonging to that event’s calls, populate linked business profiles and deduplicate vendors. Return only public business identity fields, excluding pending/rejected/withdrawn records and private application contact data. Legacy accepted applications need an explicitly linked real vendor before a public profile can appear.
16. **Confirmed Events.** Query the current vendor’s accepted applications → parent calls → unique events. Calculate current event state and divide upcoming/ongoing from past in the shared card list. Confirmed vendors retain authenticated read access after cancellation; cancelled events leave public discovery/feed.
17. **Shared UI.** One public layout/header/navigation for all roles; existing EventCard implementation reused across Home, Discover, feed, profiles and confirmed events; shared profile header/post/vendor/status cards; field/image/resource components; one cancellable loading hook. New screens use the existing tokens and font variables. Route-level lazy loading keeps the production entry bundle below the previous warning threshold.
18. **Old duplicates removed/reused.** The two former dashboards and separate workspace are replaced by contextual shared views. Catalogue forms, the event form and recruitment form are reused. Anonymous tracking is replaced by the authenticated application list. The current Home card and image service remain the original shared implementations.
19. **Cloudinary.** The existing server stream upload, secure URLs and multipart service remain operational, now authenticated. JPG/PNG/WEBP and 5 MB limits are preserved. A real browser upload verified secure URL storage, event preview and removal; shared profile/post image upload controls use the same service. Existing Home posters were also verified loaded. Only newly created QA assets are cleaned up.
20. **Build and verification.** `npm run build` succeeds; `npm run lint` succeeds; all five processing tests pass; 94 integration requests verify auth, ownership, publishing, privacy, concurrent final-slot acceptance, lineups, confirmed/cancelled events and rollback. Browser evidence covers 140 route views at 1440/1024/768/430/390, with no horizontal overflow or runtime exceptions; 14 interaction checks cover real forms/upload/logout. Twenty additional final header checks and successful UI registration for all three roles passed; see account-smoke-audit.json. No formal full accessibility certification is claimed.
21. **Manual database work.** No seed or bulk migration was run against the existing database. Preview `node scripts/migrate-accounts.js`, back up, then apply deliberately to normalize old states and replace the email/call index with vendor/call identity. Existing organizers remain public/read-only until explicitly linked to a verified account. Linking and legacy vendor guidance are in [MIGRATION.md](MIGRATION.md). Seed is optional, only for a separate empty database with `DEMO_PASSWORD`.
22. **Environment.** A fresh local server-only `JWT_SECRET` is already configured and ignored by Git. Other machines must set their own secret plus `MONGO_URI` and existing Cloudinary settings; frontend only needs `VITE_API_URL` when using another API address. `DEMO_PASSWORD` is only for optional seeds; `POSTER_IMPORT_TOKEN` only for an explicit owned poster import. No secrets are printed or added to frontend code.

Final verification: the production build, lint, five server tests and five read-only API checks passed after cleanup. The migration preview found one legacy event state, one legacy application state, six unclaimed organizers and two applications without vendor account links; no migration writes were applied.

Cleanup removed ten temporary accounts, the temporary event and its applications, and three test uploads. All thirteen original published events remain, and there are no remaining QA accounts. See [account-cleanup-audit.json](account-cleanup-audit.json).

The local app runs at port 5174 and its API at port 3000. No deployment, commit, push, teammate invitation or external submission is performed by this refactor.
